# 18. Search, filter og sortering

## Overordnet princip

> **Søgning, filtrering og sortering skal hjælpe brugeren med at indsnævre store mængder data uden at miste overblik, kontekst eller navigation state.**

Det betyder, at search/filter/sort ikke bare er kontrolelementer øverst på en liste. Det er en central del af brugerens arbejdsflow.

***

## 18.1 Hvilke sider har behovet?

Guidelines bør især gælde for:

* Haver
* Bede
* Planter
* Materialer
* Filer
* Butikker
* Medlemmer
* Invitationer
* Senere projekter/opgaver/tilbud

I dine designbeslutninger er planter, materialer, haver, filer, butikker og invitationer allerede udpeget som vigtige steder for search/filter/sort.

***

# 18.2 Søgning vs. filter vs. sortering

Vi bør skelne tydeligt:

| Funktion      | Bruges til                  | Eksempel                   |
| ------------- | --------------------------- | -------------------------- |
| **Søgning**   | Finde tekstmatch            | “lavendel”                 |
| **Filter**    | Indsnævre ud fra egenskaber | Lys = Sol                  |
| **Sortering** | Ændre rækkefølge            | Navn A–Å                   |
| **View-mode** | Ændre præsentation          | Cards / compact rows       |
| **Scope**     | Bestemme datamængden        | Aktive / arkiverede / alle |

## Designregel

> **Søgning finder. Filter indsnævrer. Sortering prioriterer. View-mode ændrer præsentation.**

Hvis de blandes sammen i UI’et, bliver brugeren usikker.

***

# 18.3 Filterbar layout

På desktop bør vi have en tydelig filterbar over listen.

Eksempel:

```text
[Søg planter...] [Lys] [Type] [Blomstring] [Sortér: Navn A–Å] [Cards/List]
```

For filer:

```text
[Søg filer...] [Filtype] [Status] [Tilknytning] [Sortér: Nyeste først]
```

For haver:

```text
[Søg haver...] [Status: Aktive] [Type] [Sortér: Senest opdateret]
```

## Designregel

> **De mest brugte filtre skal være synlige. Sjældne filtre kan ligge under “Flere filtre”.**

Det holder UI’et roligt og undgår en filterbar, der fylder hele siden.

***

# 18.4 Mobile filter drawer

På mobil bør filterbaren ikke bare presses sammen i én lang række.

Jeg vil anbefale:

```text
[Søg]
[Filtrer] [Sortér]
```

Hvor “Filtrer” åbner en drawer/bottom sheet.

## Mobilmønster

```text
Søg planter
[lavendel]

[Filtrer] [Sortér]
Aktive filtre: [Sol ×] [Staude ×]
```

## Filter drawer

```text
Filtrer planter
Lys
- Sol
- Halvskygge
- Skygge

Type
- Staude
- Busk
- Træ

[Anvend filtre]
[Nulstil]
```

## Designregel

> **Mobil skal bruge drawer/bottom sheet til flere filtre, ikke en overfyldt horisontal filterbar.**

***

# 18.5 Active filter chips

Når filtre er aktive, skal de vises tydeligt.

Eksempel:

```text
Aktive filtre:
[Sol ×] [Stauder ×] [Blå ×]
[Nulstil alle]
```

Dette er allerede nævnt som mønster i dine designbeslutninger.

## Hvorfor?

* Brugeren kan se, hvorfor listen er indsnævret.
* Brugeren kan fjerne ét filter ad gangen.
* Filtered empty states bliver lettere at forstå.
* Return-flow efter oprettelse bliver mere gennemskueligt.

## Designregel

> **Alle aktive filtre skal være synlige som chips eller tydelige filterværdier.**

***

# 18.6 Nulstil filter

“Nulstil” skal findes, når der er aktive filtre.

Der bør være to niveauer:

## Fjern enkelt filter

```text
[Sol ×]
```

## Nulstil alle

```text
[Nulstil alle]
```

## Designregel

> **Hvis brugeren kan aktivere flere filtre, skal brugeren også kunne rydde dem enkeltvis og samlet.**

***

# 18.7 Filtered empty state

Dette hænger direkte sammen med Demo10 og Demo12.

Når filtre giver nul resultater, skal UI’et ikke vise first-use empty.

## Godt

```text
Ingen planter matcher dine filtre
Prøv at ændre søgningen eller nulstil filtrene.

[Nulstil filtre]
```

## Dårligt

```text
Ingen planter endnu
[Opret plante]
```

hvis der faktisk findes planter.

## Designregel

> **Filtered empty skal forklare, at data muligvis findes, men ikke matcher de aktuelle filtre.**

***

# 18.8 Søgning

Søgning bør være enkel og umiddelbar.

## Search input bør have

* tydelig placeholder
* søgeikon hvis ønsket
* clear button
* synlig søgeterm
* filtered empty med søgetermen

Eksempel:

```text
Søg planter
lavenddel

Ingen resultater for “lavenddel”
Kontrollér stavningen, eller prøv med et bredere søgeord.

[Ryd søgning]
```

## Designregel

> **Search empty skal vise søgetermen.**

Det hjælper især ved stavefejl.

***

# 18.9 Search debounce og loading

Ved søgning bør UI’et ikke blinke eller vise empty for tidligt.

Flow:

```text
Bruger skriver → kort loading/skeleton/inline “Søger…” → resultater eller search empty
```

## Designregel

> **Søgning skal have loading state før empty state, hvis resultatet ikke er øjeblikkeligt.**

Dette hænger sammen med loading-principperne fra Demo11.

***

# 18.10 Sortering

Sortering skal være tydelig, men ikke dominere.

Typiske sorteringer:

## Haver

* Senest opdateret
* Navn A–Å
* Oprettet dato
* Status

## Planter

* Almindeligt navn A–Å
* Latinsk navn A–Å
* Lysforhold
* Blomstring
* Højde

## Materialer

* Navn A–Å
* Type
* Senest brugt
* Oprettet dato

## Filer

* Nyeste først
* Filnavn A–Å
* Filtype
* Status
* Størrelse

## Invitationer

* Status
* Udløber snart
* Nyeste først
* Email A–Å

## Designregel

> **Sortering skal afspejle brugerens typiske beslutning i den konkrete liste.**

***

# 18.11 Sortering og retning

Hvis sortering kan vendes, skal det fremgå.

Eksempel:

```text
Sortér: Navn A–Å
Sortér: Navn Å–A
```

eller ikon, men tekst er bedst.

## Designregel

> **Sorteringens retning skal være synlig i tekst, ikke kun ikon.**

***

# 18.12 View-mode

For store lister giver det mening at kombinere filter/sort med view-mode.

Eksempel:

```text
[Cards] [Liste] [Tabel]
```

## Brug

| View-mode      | Brug                              |
| -------------- | --------------------------------- |
| Cards          | Overblik og visuel scanning       |
| Compact rows   | Store lister og hurtig navigation |
| Table          | Sammenligning og tal              |
| Thumbnail grid | Filer/billeder                    |

## Designregel

> **View-mode er ikke filter. Det ændrer kun præsentationen og bør bevares som brugerens præference eller URL-state.**

***

# 18.13 Filter state i URL

Dette er vigtigt og hænger direkte sammen med navigation state.

Eksempel:

```text
/planter?search=lavendel&lys=sol&type=staude&sort=name&view=compact
```

For filer:

```text
/haver/123/filer?type=pdf&status=temporary&sort=newest
```

## Fordele

* refresh bevarer state
* back/forward virker
* return-flow virker
* links kan deles
* filtered empty er forståelig

## Designregel

> **Søgning, filtre, sortering, pagination og aktiv view-mode bør som hovedregel være URL-state.**

Dette er særligt vigtigt i de store lister.

***

# 18.14 Bevar filter ved navigation

Eksempel:

```text
Brugeren er på plantelisten:
search=lavendel
lys=sol
sort=navn
view=compact

Brugeren opretter plante
Returnér til samme filtre, sortering og view-mode
```

Hvis ny plante ikke matcher filteret:

```text
Planten er oprettet
Den vises ikke i listen, fordi det aktive filter er “Sol”.

[Nulstil filter]
```

## Designregel

> **Search/filter/sort skal indgå i return context.**

***

# 18.15 Pagination og store lister

Hvis lister bliver store, skal pagination eller virtualisering fungere sammen med filtre.

URL:

```text
/planter?page=3&search=lavendel&lys=sol
```

Ved ændring af filter bør siden normalt gå tilbage til page 1.

## Designregel

> **Når filter eller søgning ændres, bør pagination nulstilles til første side.**

Hvis ikke, kan brugeren lande på en tom side, selvom der findes resultater.

***

# 18.16 Filter scope: aktive, arkiverede, alle

Fra #5 ved vi, at arkiverede objekter bør skjules fra aktive lister som standard.

Derfor skal mange lister have status/scope:

```text
Status: Aktive
Status: Arkiverede
Status: Alle
```

eller:

```text
[ ] Vis arkiverede
```

## Designregel

> **Aktive/inaktive/arkiverede er et scope-filter og skal være tydeligt.**

***

# 18.17 Filter og permissions

Permissions kan påvirke hvilke filtre og resultater brugeren ser.

Eksempel:

* bruger må ikke se visse filer
* bruger må kun se metadata
* bruger kan ikke se medlemmer

UI skal undgå at vise filtermuligheder, der altid giver no-access.

## Designregel

> **Filtermuligheder skal afspejle den data, brugeren faktisk kan se.**

Dette bør genbesøges, når access control implementeres som service — præcis som du noterede for #6.

***

# 18.18 Filter og performance

Filter/søgning kan være tungt, især hvis:

* listen er stor
* thumbnails indgår
* fritekstsøgning rammer mange felter
* data hentes fra server
* Blazor Server skal opdatere ofte

## UI-principper

* debounce søgning
* vis “Søger…” eller skeleton ved forsinkelse
* hent metadata før thumbnails
* lazy load billeder
* undgå at filtrering genhenter originalfiler
* bevar layout under loading

## Designregel

> **Filter og search må aldrig trigge hentning af tunge originalressourcer.**

***

# 18.21 Beslutningstabel

| Situation                     | UI                                    |
| ----------------------------- | ------------------------------------- |
| Brugeren skriver søgning      | Search input med clear                |
| Søgeresultat loader           | Inline “Søger…” eller skeleton        |
| Ingen resultater pga. søgning | Search empty med søgeterm             |
| Filtre aktive                 | Filter chips + nulstil alle           |
| Ingen resultater pga. filter  | Filtered empty                        |
| Sortering valgt               | Sort label med retning                |
| Mobil med mange filtre        | Filter drawer/bottom sheet            |
| Store lister                  | Pagination/virtualisering + URL-state |
| Return-flow                   | Bevar search/filter/sort/view         |
| Arkiverede data               | Scope filter: aktive/arkiverede/alle  |

***

# Anbefalet designbeslutning

Jeg ville låse principperne sådan:

1. **Search, filter og sortering skal være tydeligt adskilte funktioner.**
2. **De mest brugte filtre vises direkte; sjældne filtre ligger under “Flere filtre”.**
3. **Aktive filtre vises som chips og kan fjernes enkeltvis.**
4. **Der skal altid være “Nulstil alle”, når flere filtre er aktive.**
5. **Filtered empty må ikke ligne first-use empty.**
6. **Search empty skal vise søgetermen.**
7. **Sortering skal vise både felt og retning.**
8. **Mobil bruger filter drawer/bottom sheet frem for overfyldt filterbar.**
9. **Search/filter/sort/view bør gemmes i URL-state.**
10. **Return-flow skal bevare search/filter/sort/view og evt. pagination.**
11. **Når filter ændres, bør pagination nulstilles.**
12. **Filter/search må ikke hente tunge originalressourcer.**
13. **Arkiverede objekter håndteres som tydeligt scope-filter.**
14. **Filtermuligheder skal respektere permissions.**

***

# Kort dokumentationstekst

Du kan bruge denne direkte:

> **Search, filter og sortering:** Søgning bruges til tekstmatch, filtre til at indsnævre ud fra egenskaber, sortering til at ændre rækkefølge og view-mode til at ændre præsentation. Aktive filtre skal vises som chips og kunne fjernes enkeltvis eller nulstilles samlet. Filtered/search empty states skal tydeligt forklare, at listen er tom på grund af søgning eller filtre — ikke fordi der ikke findes data. Search, filter, sortering, pagination og view-mode bør bevares i URL-state, så refresh, back/forward og return-flow fungerer. På mobil anvendes en filter drawer/bottom sheet, så filterbaren ikke bliver overfyldt.
